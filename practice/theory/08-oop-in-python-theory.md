# Теория · ООП в Python: особенности, недостатки и что «не работает»

> ООП в Python — «гибридное»: Python поддерживает и классы, и парадигму, но НЕ
> строго как Java/C++. Многое работает иначе — и это важно понимать заранее.

---

## 1. Особенности ООП именно в Python

### 1.1. Всё — объект, включая функции и классы
```python
def f(): ...


type(f)  # <class 'function'>
type(int)  # <class 'type'>
```
Классы сами — объекты (метаклассы). Функции можно передавать, возвращать, хранить.

### 1.2. Утиная типизация (duck typing)
Python не требует объявлять интерфейсы. Если объект «ходит как утка и крякает
как утка» — это утка:

```python
def greet(x):
    return x.name  # не важно ЧТО это, важно что есть .name


class Dog:
    name = "Шарик"


class Robot:
    name = "R2D2"


greet(Dog())  # 'Шарик'  — никаких интерфейсов!
```

### 1.3. Атрибуты класса vs атрибуты экземпляра
```python
class Point:
    kind = "2D"  # атрибут класса (общий)

    def __init__(self, x, y):
        self.x = x  # атрибут экземпляра
        self.y = y
```

### 1.4. Никаких настоящих «приватных» полей
`_x` и `__x` — это соглашение, а НЕ защита:
```python
class A:
    def __init__(self):
        self._pv = 1  # «приватное» по договорённости
        self.__m = 2  # «name-mangling»


a = A()
a._pv  # работает! соглашение, не запрет
a._A__m  # доступ к __m через переименование
```
**По-настоящему инкапсуляции в Python нет** — только договорённости и свойства.

### 1.5. Свойства (`property`) — управляемый доступ вместо геттеров/сеттеров
```python
class Temperature:
    def __init__(self):
        self._c = 0

    @property
    def celsius(self):
        return self._c

    @celsius.setter
    def celsius(self, v):
        if v < -273:
            raise ValueError("слишком холодно")
        self._c = v
```
Это замена `getCelsius()`/`setCelsius()` из Java — идиоматичнее.

### 1.6. Жёсткое наследование только от одного класса
Но есть **миксины** (множественное наследование), 
и **абстрактные базовые классы** через `ABC`.

### 1.7. `dataclass` — «полу-классы» для данных
```python
from dataclasses import dataclass


@dataclass
class Point:
    x: float
    y: float


# автоматически: __init__, __repr__, __eq__, __hash__
```

### 1.8. Протоколы и структурная подтипизация (3.8+)
```python
from typing import Protocol


class Named(Protocol):
    name: str  # любой с .name — это Named
```

### 1.9. Магические методы («дабл-андерскоры»)
`__init__`, `__repr__`, `__eq__`, `__len__`, `__add__`, `__getitem__` —
переопределение операторов и встроенных функций через методы.

## 2. Недостатки ООП в Python

| Недостаток | Суть |
|---|---|
| **Инкапсуляция не настоящая** | приватные поля — только `_`-соглашение, доступ публичен |
| **Нет true-abstract methods** без ABC | класс с `raise NotImplementedError` в методах — это симуляция, не гарантия |
| **Медленнее из-за динамики** | атрибуты и lookup в рантайме; объекты тяжелее C++/Java |
| **Множественное наследование = путаница** | конфликты имён, `super()` в MRO сложно понять новичку |
| **Динамическая типизация → ошибки в рантайме** | опечатка в атрибуте ловится только при запуске |
| **Перегрузка методов/операторов ограничена** | нет «перегрузки по типу» как в Java/C++; один метод на имя |
| **Глобальное состояние легко утекает** | класс-атрибуты общие — случайное изменение видно всем |
| **Нет классических интерфейсов** | программа часто на доверии к duck typing, а не к контрактам |

## 3. Что в Python «не работает» / работает иначе (важно!)

### 3.1. Приватности нет — точка
В Java `private` — защита на уровне языка. В Python это `_`-соглашение:
компилятор не помешает, только твой коллектив договорится. **Защиты нет.**

### 3.2. Наследование от `object` по умолчанию, но нет виртуальности как в C++
Все методы «виртуальные» по умолчанию (динамическая диспетчеризация). Это удобно,
но быстрее съедается производительность.

### 3.3. `super()` при множественном наследовании ведёт себя неочевидно
Порядок MRO сложный:
```python
class A:
    pass


class B(A):
    pass


class C(A):
    pass


class D(B, C):
    pass


D.__mro__  # D, B, C, A, object
```
И это влияет на `super().__init__` — новички часто ошибаются.

### 3.4. НЕТ перегрузки методов по числу/типу аргументов
В Java: `add(int)`, `add(int,int)` — два метода. В Python:
```python
def add(*args, base=0): ...  # один метод, сам разбирай аргументы
```

### 3.5. «Интерфейсы» реализуемые, но неявные
В Java `implements Interface`. В Python — протоколы/duck typing:
объект «реализует» интерфейс автоматически, если у него есть нужные методы.
Проверка — только в рантайме.

### 3.6. Конструктор только один — `__init__`
Нет перегрузок конструкторов. Разные способы создания — через `@classmethod`
(фабрики):
```python
class Money:
    def __init__(self, amount):
        self.amount = amount

    @classmethod
    def from_dollars(cls, amt):
        return cls(amt * 100)
```

### 3.7. `staticmethod` — просто фенкция внутри класса
Работает как обычная функция, без `self`/`cls`. Но её можно заменить обычной
функцией вне класса — статику в Python часто не используют.

### 3.8. Множественное наследование разрешено, интерфейсов нет
Это мощно, но опасно. Python решил «разрешить и пусть распутываются через MRO»,
вместо строгого «один родитель + много интерфейсов» в Java.

### 3.9. `private`-инг через name-mangling — `__x`
`__x` в классе переименуется в `_ClassName__x`. Это:
- НЕ защита, просто мешает случайным столкновениям имён в наследовании;
- легко обходится.
Не путай с приватностью.

### 3.10. Нельзя навсегда запретить изменение атрибута
`s__slots__` уменьшает память и запрещает случайные новые атрибуты, но это
оптимизация, а не защита.

---
## 4. Резюме

Python ООП удобен своей **гибкостью** (duck typing, свойства, dataclass), но
платишь **отсутствием жёстких гарантий**: настоящей инкапсуляции/интерфейсов
нет и не будет — это «контракты по договорённости» между разработчиками.
Для жёсткой дисциплины используют mypy (`Protocol`, `final`, `@dataclass(frozen=True)`)
и линтеры — они возвращают часть защит, потерянных из-за динамики.
