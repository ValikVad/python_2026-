
# Переменные окружения (Environment Variables) в Python

## 1. Введение: Суть и история проблемы

**Что такое переменные окружения?**
Это именованные переменные с данными, которые хранятся не в исходном коде вашей программы, а на уровне операционной системы.

**Зачем они нужны?**
Главная цель — отделение конфигурации и секретов от логики приложения. В переменных окружения хранят:

* Токены ботов и API-ключи.
* Пароли и URL для подключения к базам данных.
* Флаги режима работы (например, `DEBUG=True` для локальной разработки и `False` для продакшена).

**Как делали раньше и почему это плохо?**
Раньше пароли часто "хардкодили" прямо в скриптах:

```python
# Никогда так не делайте
DB_PASSWORD = "super_secret_password_123"

```

Проблема: любой, кто имеет доступ к исходному коду (например, через GitHub), получает полный доступ к базе данных. Другой старый способ — глобальный экспорт в терминале Linux (`export DB_PASSWORD=123`), но при перезагрузке компьютера или закрытии терминала эти данные теряются.

## 2. Эра `.env` файлов и безопасность

Для локальной разработки постоянный ввод команд в консоль неудобен. Стандартом стал файл `.env` — обычный текстовый файл в корне проекта, где переменные хранятся в формате `КЛЮЧ=ЗНАЧЕНИЕ`.

```env
# Пример файла .env
DEBUG=True
DB_PORT=5432
SECRET_KEY=hj34$k@ksdf9

```

> **ПРАВИЛО БЕЗОПАСНОСТИ:** Файл `.env` **всегда** должен быть добавлен в `.gitignore`. Он никогда не должен попасть в систему контроля версий.

**Файлы-шаблоны (.env.example)**
Поскольку реальный `.env` скрыт, другие разработчики не узнают, какие настройки нужны проекту. Для этого создается пустой шаблон, который заливается в Git:

```env
# Файл .env.example (сохраняется в репозитории)
DEBUG=True
DB_PORT=5432
SECRET_KEY=your_secret_key_here

```

Новый разработчик копирует этот файл, переименовывает в `.env` и вписывает свои локальные доступы.

## 3. База: Как Python работает с окружением из коробки

Единственный базовый мост между Python и переменными операционной системы — это встроенный модуль `os`.

Есть два основных способа получить переменную, и между ними огромная разница:

```python
import os

# Способ 1: Жесткое чтение (os.environ)
# Если ключа 'SECRET_KEY' нет в системе, программа упадет с ошибкой KeyError
api_key = os.environ['SECRET_KEY']

# Способ 2: Безопасное чтение (os.getenv)
# Если ключа нет, вернет None. Программа продолжит работу.
db_host = os.getenv('DB_HOST')

# Также getenv позволяет задать значение по умолчанию:
port = os.getenv('PORT', '8080') 

```

## 4. Библиотеки и проблема типизации

Python не читает файлы `.env` автоматически. Для этого нужны сторонние библиотеки.

### Классика: python-dotenv

Устанавливается через `pip install python-dotenv` (или `uv add python-dotenv` / `poetry add python-dotenv`).

```python
import os
from dotenv import load_dotenv

# Находит файл .env и загружает его содержимое в os.environ
load_dotenv() 

print(os.getenv('DB_PORT'))

```

### Проблема типов (Всё есть строка)

Главная проблема `.env` — операционная система не знает типов данных (int, list, bool). Всё считывается как текст.

```env
DEBUG=False
MAX_CONNECTIONS=10

```

В Python это приведет к багу, если не привести типы вручную:

```python
debug = os.getenv('DEBUG') # Это строка "False"
if debug:
    # Любая непустая строка в Python это True
    print("Режим отладки включен!") 

```

### Решение: библиотека environs

Библиотека `environs` решает проблему типизации на лету:

```python
from environs import Env

env = Env()
env.read_env() # читает .env файл

# Автоматически конвертирует типы
debug = env.bool("DEBUG", default=False) # Теперь это настоящий bool
max_conn = env.int("MAX_CONNECTIONS")    # Теперь это int
hosts = env.list("ALLOWED_HOSTS")        # Превратит "localhost,127.0.0.1" в список

```

*Примечание: В крупных проектах для этого часто используют фреймворк `pydantic-settings`, который позволяет валидировать целые конфигурационные классы, но `environs` отлично подходит для быстрых и элегантных решений.*

## 5. Интеграция с инструментарием (venv, Poetry, uv)

Современные менеджеры пакетов позволяют передать переменные в Python еще до его запуска, избавляя от необходимости писать `load_dotenv()` в самом коде.

**1. Взлом классического `venv**`
В стандартном `venv` переменные не подхватываются сами. Но можно открыть скрипт активации (в Windows: `venv\Scripts\activate.bat`, в Linux: `venv/bin/activate`) и дописать туда экспорт вручную:

```bash
# Добавляем в конец файла activate:
export DEBUG=True
export DB_PORT=5432

```

Теперь при каждом включении виртуального окружения переменные будут загружаться в систему автоматически.

**2. Менеджер зависимостей Poetry**
По умолчанию Poetry игнорирует `.env` файлы. Чтобы он начал их читать, нужно один раз установить официальный плагин:

```bash
poetry self add poetry-plugin-dotenv

```

После этого любая команда (например, `poetry run python main.py`) автоматически найдет `.env`, прочитает его и передаст переменные вашему скрипту.

**3. Ультрабыстрый uv**
В менеджере `uv` поддержка окружения встроена нативно, но ради безопасности разработчики отключили автоматическое чтение. `uv` требует явного указания, какой файл использовать. Для этого применяется специальный флаг:

```bash
uv run --env-file .env python main.py

```

## 6. Эволюция подходов: Сравнение библиотек

Когда проект растет, меняются и требования к работе с переменными окружения. Давайте сравним три главных инструмента.

### 1. python-dotenv (Базовый уровень)
Отличный выбор для простых скриптов и парсеров.
* **Плюсы:** Максимально прост в освоении, стандарт де-факто.
* **Минусы:** Возвращает только строки. Нет встроенной проверки, все ли нужные переменные на месте.
* **Пример:** `port = int(os.getenv("PORT", 8000))` — приходится вручную оборачивать в `int()`.

### 2. environs (Продвинутый уровень)
Создан для тех случаев, когда ручной перевод строк в числа и списки начинает раздражать.
* **Плюсы:** Умеет на лету конвертировать типы (int, bool, list). Если обязательной переменной нет, сразу выдаст понятную ошибку, а не сломает код где-то в середине.
* **Минусы:** Требует отдельной инициализации объекта `Env()`.
* **Пример:** `port = env.int("PORT", 8000)` — выглядит гораздо чище.

### 3. pydantic-settings (Промышленный стандарт)
Используется в серьезных backend-проектах.
* **Плюсы:** Конфигурация описывается как Python-класс со строгой типизацией. Автоматическая валидация всех полей перед стартом приложения.
* **Минусы:** Избыточен для маленьких скриптов на 100 строк кода.
* **Пример:**
  ```python
  from pydantic_settings import BaseSettings

  class Settings(BaseSettings):
      db_port: int
      debug_mode: bool = False

  # Pydantic сам найдет переменные DB_PORT и DEBUG_MODE в .env
  # сам проверит типы и упадет с ошибкой до старта, если в port написали буквы
  config = Settings()
    ```


## 7. Топ типичных ошибок (Как не надо делать)

1. **Случайный слив секретов в GitHub.**
*Ошибка:* Забыли добавить `.env` в `.gitignore` перед `git commit`. Специальные боты сканируют публичные репозитории каждую секунду. Ваш токен от облака или криптобиржи будет скомпрометирован мгновенно.
2. **Падение из-за `KeyError`.**
*Ошибка:* Использование `os.environ['KEY']` там, где переменная может отсутствовать. Всегда используйте `os.getenv('KEY')`, если не хотите, чтобы программа жестко падала при старте.
3. **Ловушка булевых значений.**
*Ошибка:* Написать в конфиге `DEBUG=False` и проверять `if os.getenv('DEBUG'):`. Используйте приведение типов или библиотеку вроде `environs`.
4. **Пробелы в `.env` файле.**
*Ошибка:* `API_KEY = 12345` (с пробелами до и после равно).
*Правильно:* `API_KEY=12345`. Лишние пробелы могут быть восприняты как часть имени переменной или её значения.
